# Tab 运行账本与运行态数据面

## Summary

一次 tab 派发在 `~/.pi/agent/tab-runs/`（env `PI_TAB_RUNS_DIR` 覆盖）下产生**三个独立文件**：派发账本 `<runId>.json`（主会话派发时写一次）、遥测状态 `<runId>.state.json`（tab 进程自己写）、终态结果 `<runId>.result.json`（tab-finish / 兜底写入器）。三者**不是同一份记录的三段**：写者不同、生命周期不同、字段面不同，只有 `id` 共享。

对外（GUI/daemon）的可见面有两条且**互不相同**：`/v1/snapshot.runs[]` 是 **journal 投影**（只有 dispatch/terminal 事件带的字段，**没有** state 的 `phase`/`turn`/`pid`/`heartbeatAt`），`/v1/sessions/:id/transcript` 是**会话 JSONL 投影**（有 toolCall 行，能反映「现在在哪一步」）。两者都不是「run 台账直读」。**daemon 没有任何直读 `tab-runs/` 的端点**（`session-title.ts` 的台账读是 `/v1/sessions` 标题解析专用，不下发原始记录）。

## Current Contract

### 三文件：写者、路径、生命周期

| 文件 | 路径函数 | 写者（file:line） | 写入时机 | 权威性 |
|---|---|---|---|---|
| 派发账本 `<runId>.json` | `tabDispatchPath`（`tab-runs.ts#L557`） | `writeTabDispatch`（`#L618`，内部 `writeJsonAtomic` 原子写 `#L570`） | **派发时 1 次**（+ `launch_failed` 回写 1 次）。调用点：`index.ts#L3418`/`#L3421`（local master tab）、`#L4999`/`#L5007`/`#L5012`（direct `/launch`）、`launch-workflow.ts#L115`/`#L154`/`#L160`、`one-shot-tab.ts#L86`/`#L89`、`trace-fusion/launch-workers.ts#L243`/`#L378`/`#L260`/`#L272`/`#L395`/`#L409` | **派发事实的权威**（`TabDispatchRecord`，`#L30-L45`）。之后**永不更新**（除了 `dispatchStatus`→`launch_failed` 的那一次整份覆盖） |
| 遥测状态 `<runId>.state.json` | `tabStatePath`（`#L561`） | `writeTabState`（`#L816`），唯一调用方 = `registerTabTelemetry` 的 `writeState`（`tab-runs-runtime.ts#L213-L230`）+ 心跳（`#L250`）+ 终态冗余（`#L333`/`#L431`） | tab 进程内**每次生命周期事件**覆盖写；心跳每 30s（`HEARTBEAT_MS`，`#L241`） | **运行态的权威**（`TabState`，`#L514-L555`）。整份覆盖写 ⇒ 后写者即全量真相 |
| 终态结果 `<runId>.result.json` | `tabResultPath`（`#L565`） | `tab-finish` 工具（`tab-runs-runtime.ts#L420` 的 `writeJsonAtomic`）或 `writeSettlementFallback`（`#L161`） | tab 自报终态 1 次；或 `agent_settled` 时兜底 1 次（`#L307-L326` 接线） | **工作流终态的权威**（`TabResult`，`#L66-L83`），优先级最高 |

三者的路径规则见 `tab-runs.ts#L557-L575`；`.state.json` / `.result.json` 目录扫描时一律排除（`listTabDispatches` `#L635-L650`、`archiveStaleTabRuns` `#L663`），只有 `<runId>.json` 算「派发账本」。

### 字段面

- **`TabDispatchRecord`**（`tab-runs.ts#L30-L45`）：`id` / `version:1` / `taskId` / `mode`（`workflow|research|execute|adaptive|trace`）/ `title?` / `cwd`（解析后绝对路径，决定 session 桶）/ `requestedModel?` / `dispatchedAt` / `dispatchStatus`（`dispatched|launch_failed`）/ `error?` / `direct?`。**无状态字段**——派发账本只描述「派发了什么」。
- **`TabState`**（`#L514-L555`）：`id` / `phase`（`attached|working|waiting|completed|failed|cancelled|orphaned`）/ `turn`（`working|idle|error|unknown`）/ `terminal`（只有显式终态信号才 true）/ `sessionPath?` / `pid?` / `lastActivityAt?` / `heartbeatAt?` / `currentToolStartedAt?` / `lastAssistantText?` / `lastStopReason?` / `usage?`（`TabUsage`：`input/output/cacheRead/cacheWrite/cost/turns`）/ `error?`。
  - **`heartbeatAt` 与 `lastActivityAt` 必须分开读**（`#L523-L535`）：心跳只证「进程活 + 事件循环在跑」，长工具期间 `lastActivityAt` 会冻住。判死口径明写为 `pid` 探活 ∨ `heartbeatAt` 距今 > 90s（3 个心跳周期）。
- **`TabResult`**（`#L66-L83`）：`id` / `taskId` / `status`（四态 `completed|failed|cancelled|unconfirmed`）/ `finishedAt` / `summary?` / `finalText?` / `artifacts?` / `reportPath?` / `openIssues?` / `usage?` / `autoGenerated?`。**不变量**：`status==="unconfirmed"` ⟺ `autoGenerated===true`（`isUnconfirmedFallback` `#L487` 是唯一判据）。

`registerTabTelemetry`（`tab-runs-runtime.ts#L178`，接线 `index.ts#L3354`）只在**已有 tab 身份的进程**里生效（`resolveRunId()` 取 CLI flag `--tab-run-id` 或 env，子 agent 不拥有 tab 身份，`#L193-L197`）：

| pi 事件 | 写什么 | file:line |
|---|---|---|
| `session_start` | `phase:"attached"`, `turn:"idle"`, `sessionPath`, `pid` | `#L255-L258` |
| `agent_start` | `phase:"working"`, `turn:"working"` | `#L260-L262` |
| `tool_execution_start` | `working/working` + `currentToolStartedAt` | `#L264-L270` |
| `tool_execution_end` | `working/working` + 清除 `currentToolStartedAt` | `#L273-L275` |
| `message_end`（仅 assistant） | 内存累加 `usageAccum`（复合去重键 `id\|timestamp\|responseId`，`#L288-L290`）+ `lastAssistantText`(截 2000) / `lastStopReason`；**不单独写盘** | `#L277-L305` |
| `agent_settled` | `phase:"waiting"`, `turn:"idle"` + **兜底 result 写入**（`writeSettlementFallback`） | `#L307-L326` |
| `session_shutdown`（非终态） | `phase:"orphaned"`, `turn:"unknown"`, `terminal:false`, `error:"session shutdown without explicit tab-finish"` | `#L329-L347` |
| `tab-finish` 工具 | 先 `writeJsonAtomic(result.json)`，再 `writeTabState(phase=终态, terminal:true)` | `#L420` / `#L431-L438` |

### `state.json` 与 `<runId>.json` 的关系（谁权威、如何同步）

**两者之间没有任何同步机制**——它们从不互相读改写：

1. `state.json` 的写者（tab 进程）**只在自己进程内**持有 `phase/turn/usage` 状态，从 `session_start` 起每次事件重建整份对象（`writeState` `#L217`），唯一读回的场景是心跳的读-改-写（`#L249`）。它**不读** `<runId>.json`（除 `writeSettlementFallback` 读 dispatch 判 `taskId` 前缀，`#L120`）。
2. `<runId>.json` 的写者（主会话）**从不改** `state.json`/`.result.json`；`archiveStaleTabRuns` 会**整体搬移**三个文件到 `_archived/`（`#L745-L760`：`[dispatchPath, resultPath, statePath, notifiedPath]` 逐个 rename）。
3. 真正的「合并判定」在**读侧**：`buildTabStatusView`（`#L879-L890`）一次读三份 + JSONL 探活，交 `composeTabStatus`（`#L915`）按**固定优先级 result → state → JSONL 探活**合成 `TabStatusView`（`#L895-L909`）。所以「权威」是**按字段分层**的：
   - `phase`/`terminal`/`resultMissing` 由 `composeTabStatus` 派生（result 优先、state 次之、探活兜底，`#L928`/`#L966`/`#L985`）；
   - `usage`/`lastAssistantText` 取 result 优先、state 兜底（`#L945`/`#L961`/`#L978`）；
   - `dispatch`/`state`/`result` 三个原始对象**原样挂在视图上**（`#L897-L903`），调用方自己看。

**`archiveStaleTabRuns` 的归档判据**（`#L653-L766`）：默认 72h（`maxAgeHours=72`）；**「非终态就不归档」**——终态证据三条任一即可（`#L675-L684`）：① `state.phase ∈ {completed,failed,cancelled,orphaned}` ② `state.terminal===true` ③ 存在 result 文件**且不是兜底 unconfirmed**（RF-1 收窄，`isUnconfirmedFallback`）。三者全无 ⇒ 保守不归档。默认目录 `_archived/`（`TAB_RUNS_ARCHIVE_DIR` `#L1041`）。

### 对外可见面：两条投影，都不是台账直读

**A. `/v1/snapshot.runs[]` = journal 投影**（源链）：

```
tabDispatchToRuntimeEvent (adapters/tab-run.ts#L51-L78)  ─┐
tabResultToRuntimeEvent   (adapters/tab-run.ts#L122-L148) ─┴→ emitRuntimeEventOnce (journal)
   → listRuntimeEnvelopes → rebuildFromEnvelopes (projector.ts#L110-L232)
   → buildRunsSection (snapshot.ts#L312-L327)  → RuntimeSnapshot.runs (snapshot.ts#L118)
   → buildSnapshotView (server.ts#L861-L884)   → GET /v1/snapshot (server.ts#L1841-L1860)
```

- **address 形状**：`tabRunAddress(runId)` = `` `run://tab/${tabRunId}` ``（`address.ts#L46`）；`runId` 形如 `tab_<base36 时间戳>_<4 位随机>`（`newTabRunId`，`tab-runs.ts#L133`）。
- **写点**：dispatch 侧 `index.ts#L3419`/`#L3422`/`#L5001`/`#L5008`/`#L5013` + `launch-workflow.ts#L117`/`#L155`/`#L161` + `one-shot-tab.ts#L87`/`#L90`；result 侧**唯一** = `event-bus.ts#L244`（fs.watch 观察到 `*.result.json` 后）。
- **逐字段来源**（`projector.ts#L146-L225`）：

| ProjectedRun 字段 | 来源 | 何时出现 |
|---|---|---|
| `subject` | `tabRunAddress(dispatch.id)` / `result.id` | 恒有（dispatch 事件携带） |
| `status` | dispatch 分支恒 `"dispatched"`（`#L157`）；terminal 分支由**事件 type** 派生（`subjectStatusFromType` `#L226-L229`），**不读 `payload.status`** | 终态只有 `completed/failed/cancelled`（`launch_failed → failed` 显式映射 `#L133-L136`） |
| `executionKind` | `payload.executionKind`（恒 `"tab"`，`tab-run.ts#L67`/`#L137`） | 212/212 实测有（1 条例外为 `run.unconfirmed` 的单事件、无 dispatch） |
| `externalTaskId` / `mode` / `title` / `cwd` / `requestedModel` | dispatch payload（`tab-run.ts#L66-L72`） | `requestedModel` 只在派发时显式给过才在（实测 12/212） |
| `dispatchedAt` | `payload.dispatchedAt`（域时间，缺省回落 `envelope.at`，`#L164`） | 恒有 |
| `actualModel` | **恒 `"unknown"`**（`#L163`，观测遥测未采集） | 恒有 |
| `status`（终态分支）+ `summary` / `artifacts` / `reportPath` / `openIssues` / `error` / `usage` / `finishedAt` | terminal payload（`tab-run.ts#L135-L146`） | 只在终态事件里出现 |
| `lastEventAt` / `lastDedupeKey` / `updatedAt` | 终态事件元数据（`#L218-L220`） | 只在终态分支出现 |

- **投影不认识 `run.unconfirmed`**：`applyEvent`（`#L124-L144`）的 `switch` 只列 `run.dispatched` / `run.launch_failed` / `run.completed|failed|cancelled`，其余落 `default → return false`（记 dedupe 但不投影）。⇒ 兜底 unconfirmed 结果**在 snapshot 里表现为 `status:"dispatched"`**，但磁盘上有 `.result.json`（实测 3 条两者并存）。
- **`runs[]` 不含 state 字段**：`RunView = ProjectedRun` 原样（`snapshot.ts#L86`，注释明写「无 tab-runs phase——open issue 1」）。**要 `phase/turn/pid/heartbeatAt` 必须另外读 `tab-runs/*.state.json`，而 daemon 没有这个端点。**

**B. `/v1/sessions/:id/transcript` = 会话 JSONL 投影**（详见 [[GUI 消息管道与延迟贡献项]]）：这是唯一能看出「现在在哪一步」的对外可见面——`toolCall` 行带 `name` / `arguments` / `status: running|done|error` / `output`（`transcript.ts#L79-L95`）。tab 的 `sessionPath` 由 `session_start` 写进 `state.json`（`#L257`），但**实测 37 份 state 全部没有 `sessionPath` 字段**（`validateTabState` 保留它 `#L789-L790`，但写入侧对象里 `sessionPath` 只在 `session_start` 那次 extra 里 ⇒ 后续 `writeState` 重建时不带，与 `pid` 曾经的丢失形态同型）。⇒ 从 `tab-runs/` 拿不到「哪个 session 属于这个 runId」，只能靠 `cwd` 桶 + 首条 user 前缀反查（`probeSessionsForDispatch` `#L841`）或 `links.jsonl`（`recordLink kind:"tab"`，实测 212/212 快照 run 都能在 links 里找到 targetId 映射）。

## 与 async run 字段的对齐/差异

见 [[异步 Run 控制面（list / kill）]] 的字段面权威表。关键差异：

| 维度 | tab run（三文件） | async subagent（单文件 `<runId>.json`） |
|---|---|---|
| 载体数 | **3 文件 + journal** | 1 文件 |
| 运行中进度 | `state.json` 的 `phase/turn/currentToolStartedAt/heartbeatAt`（30s 心跳） | `recentCalls`/`lastToolTurn`/`turnClock`（≤1 次/5s 节流）+ `lastActivity`（≤1 次/5s） |

| 会话 JSONL | **有**（tab 是真实 pi 会话） | **无**（`--no-session` 固定旗标，`runner-argv.ts#L70`） |
| daemon 端点 | 经 journal 进 `/v1/snapshot.runs`（有，但只剩 dispatch/terminal 字段） | **有**：`GET /v1/runs`（2026-10-22 M1 新增，只读卡片投影；契约页 [[异步 Run 卡片端点（GET /v1/runs）]]） |
| 工具调用可见 | 经 `/v1/sessions/:id/transcript` 的 `toolCall` 行 | 只有 `recentCalls` 里的 `tool`/`argsDigest`/`ts`/`turn`（无 result preview） |

## 已知边界（勿当成已解决）

- **`runs[]` 无运行态**：`phase`/`turn`/`pid`/`heartbeatAt`/`currentToolStartedAt` 一个都不在 snapshot 里。要在 GUI 显示「这一步在跑什么工具」必须走 transcript（会话行）或新增直读 `state.json` 的端点。
- **state 的 `pid`/`heartbeatAt` 只在活着的 tab 上有**（4/37）——因为终态 `writeTabState`（`#L431-L438`）与 `session_shutdown`（`#L333-L345`）都**重建对象不带 `pid`**。⇒ 想靠 state 判「这个 run 的进程还在吗」，只有非终态的那几份有意义。
- **`sessionPath` 恒缺失（0/37）**：`writeState` 重建时不带 ⇒ 从台账无法定位会话文件，只能靠 cwd 桶 + 前缀探活或 links.jsonl。
- **`run.unconfirmed` 不在 projector 词表**：兜底结果永不改变 `runs[].status`，「有 result 但显示 dispatched」是**结构性**的。
