# tab 存活判定的三处缺口

> 校准状态：**current（2026-11-02 源码级核实 + 26 个 state 文件全量交叉 + 独立顾问复核）**
> 关联：`session-liveness-contract.md`、`tab-run-reclaim.md`
>
> 本文记录 `tab-status` / `reclaim-tabs` 判活的三处结构性缺口。
> 初版诊断（2026-11-02 凌晨）**有三条错**，经 `shuai/gpt-6.1-sol` 独立复核后更正，本文是更正后的版本。

---

## 现象

一个 tab（`tab_mvyiqvwe_58gz`，pid 528）在 00:28:42 最后一次 read 后进程消失，但：

```
tab-status   → unconfirmed (resultMissing)
state.json   → phase=working / lastStopReason=toolUse / heartbeatAt=00:30:11
```

看起来像「进程死了但状态没更新」。

---

## 我最初的三条错（如实登记）

### 错① 「进程死亡从未被检测，没有代码把 phase 改成 orphaned」

**错。** `tab-runs-runtime.ts:346` 早就有：

```ts
pi.on("session_shutdown", () => {
    const runId = resolveRunId();
    if (!runId) return;
    if (!finished) {
        writeTabState(runsDir, runId, { id: runId, phase: "orphaned", turn: "unknown", ... });
    }
});
```

**未覆盖的是「没触发这个事件的退出」**：崩溃、强杀、运行旧版本、写盘失败。

### 错② 「state 的 mtime 停在死亡时刻，时间戳是准的」

**错。** state 里有两个时间字段，我只看了一个：

```
lastActivityAt = 00:29:01.674Z
heartbeatAt    = 00:30:11.627Z   ← 晚 70 秒，我漏看了
```

`mtime` 记的是**最后写盘**，不是死亡时刻。而且事件循环阻塞也会让心跳停 —— 停更 ≠ 死亡。

### 错③ 漏了第三种解释：`unconfirmed` 来自更早的一次 aborted

**这是最关键的一条。** 实读该 tab 的 result 文件：

```
result 文件  08:27:40 写入   status=unconfirmed  autoGenerated=true
                            summary="...lastStopReason=aborted（可能忘记回报）..."
state 文件   08:30:11 (heartbeatAt)  phase=working
```

**result 比 state 早 2.5 分钟。** 而 `composeTabStatus`（`tab-runs.ts:938`）第 1 步就返回：

```ts
// 1) 显式结果：唯一工作流终态来源
if (result) {
    // 1a) 兜底结果（RF-1）：**不是终态**
    if (result.status === "unconfirmed") {
        return { ..., phase: "unconfirmed", turn: state?.turn ?? "idle",
                 terminal: false, resultMissing: true, ... };
    }
```

**result 优先级最高，完全不看 `state.phase`。** 所以 `tab-status` 显示的 `unconfirmed` 反映的是
**08:27:40 那次 `aborted` 留下的旧兜底**，而不是「最后回合结束」——不能据此推断进程死亡。

---

## 真正的缺口（三条，各自独立）

### 缺口 1：`composeTabStatus` 没有进程存活维度

`probe` 是 `SessionProbe`（读会话 jsonl：`messageCount` / `lastStopReason` / `usage`），
**只看会话文件，不看进程**。所以：

- 进程活着但会话文件不更新 ⇒ 看起来像卡住
- 进程死了但会话文件完整 ⇒ 看起来像 idle
- 旧兜底 result 存在 ⇒ 一律显示该 result 的 status

### 缺口 2：`livenessFromTabState` 全仓零调用

`session-liveness.ts:93` 有现成的 `livenessFromTabState()`，`liveness.ts:174` 有 `probePidState()`
（三态 `alive`/`dead`/`unknown`，含 Windows EPERM 特判 + 枚举兜底）。
**两者都只在测试里被用到，生产路径（`composeTabStatus`）一次都没调。**

### 缺口 3：`session_shutdown` 只覆盖优雅退出

崩溃 / 强杀 / 旧版本 / 写盘失败 ⇒ `phase` 永久停留在死前的 `working`。

---

## 修法：优先读取侧（与 sol 建议一致）

**不做 (a) 写入侧补强**（退出前自写无法覆盖强杀，且已有 `session_shutdown` 钩子，补齐边际收益低）。

做 **(b) 读取侧**：

1. `tab-runs.ts` 的 `composeTabStatus` 增加独立维度 `liveness: { state, basis, observedAt }`，
   **不覆盖 `phase`**（保留 `unconfirmed` 的保守语义 —— 它是「未回报」，不是「死亡」）
2. 复用 `liveness.ts::probePidState` 三态，批量查询 + 超时
3. `tab-status` / `reclaim-tabs` 两个工具共用并**展示**这个维度

### 三个必须注意的坑（sol 明确指出）

| 坑 | 说明 |
|---|---|
| **Windows EPERM 不能判死** | `probePidState` 已处理：EPERM 时查进程表，表里没有才判 dead |
| **PID 复用** | 必须配启动时间身份校验（`processStartedAt()` 已有） |
| **`alive > dead` 不能跨 run 混用** | `mergeEvidence` 的优先级只适用**同一逻辑会话的多实例**，不能拿来比较不同 runId |

---

## 验证要求（改完后必做）

用**真实工具入口**（不是单测直调）验证四种场景：

1. 强杀（`taskkill /F`）⇒ 应显示 `liveness.state=dead` 而 `phase` 保持原值
2. 旧兜底 result 存在但会话仍在继续 ⇒ 应同时显示 `unconfirmed` + `liveness.state=alive`
3. 事件循环长阻塞（心跳停但进程活）⇒ 应显示 `liveness.state=alive`
4. 探针失败（pid 缺失 / tasklist 不可用）⇒ 应显示 `unknown`，**不得**判死

---

## 教训

**同一个错误今晚犯了三次**：只看单一快照就下确定性结论。

| # | 事件 | 错在哪 |
|---|---|---|
| 1 | `delivery-reconciler.json` | 断言「cursor 卡死 12 小时」，几秒后重读发现它在动 |
| 2 | frontier「5 个项目全 Working」 | 把一次采样当稳态 |
| 3 | 本文的 tab 判活 | 只看 `lastActivityAt` 漏了 `heartbeatAt`；只看 state 漏了更早的 result |

**共同点：把「一个时间点的观测」当成「系统性质」。**

判活要同时看三个证据源（state 时间戳 / result 文件 / 进程表），任一单独都不够。
